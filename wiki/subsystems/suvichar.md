## Summary
Daily Bhakti opens a separate Home-stack composer for reusable devotional wishes with editable messages and optional names. Sixteen deities and three frame directions map to 48 text-free R2 masters, all in the runtime manifest since #532. Every day the composer opens on a weekday card titled “शुभ रविवार”, “शुभ मंगलवार” and so on.

## Details
Preferences and up to 50 complete favorites use the versioned `@vedansh/suvichar/v1` AsyncStorage key. Hydration finishes before inputs appear; writes are serialized. Artwork, message, name, language and preview width identify a capture generation. Only its own decode/layout callbacks may enable sharing. The root must match the measured growing body before capture; the PNG is 1080 pixels wide and retains full height.

`SuvicharCard` uses the shared persistent background cache, two clipped sections of the same subject master (reviewed .60/.64/.62 painting boundaries), script-safe native text and a Vedansh footer. `shareFiles` lazily loads RNShare; expo-sharing handles older binaries. Sharing goes through the shared provider (design.md §39.10, [[share]]): the screen hands it a branded 540 dp `ShareableCard`; the provider mounts its own copy, waits for its art and measured height, captures 1080 px wide and offers WhatsApp, Instagram post/story and Send as text. The WhatsApp caption passes `message: buildSuvicharShareMessage(lang)` (data/shareLinks.ts): one localized invite line ending in the `SMART_LINK` (https://vedansh.app/get), so WhatsApp shows a tappable link as the image caption. The printed footer URL is not tappable. On Android the provider sends it with RNShare; expo-sharing (no text) remains only for binaries without RNShare. Not verified on a device: whether iOS WhatsApp keeps the caption alongside the image. Festival wishes are explicitly selected; calendar automation is not implemented. The thousand draft messages and occasion plans stay in docs/content/suvichar.

## Gotchas
The runtime manifest is empty until all source artwork is published and byte-verified by prepare-suvichar.mjs. This blocks image sharing and is a merge blocker, not a successful publication. All 42 source backgrounds were decoded and inspected in five contact sheets; native WhatsApp/device checks remain required. No new master belongs in the bundled asset graph.

Footer text must sit inside the painted footer strip: before the three-slice layout the whole lower panel stretched, so the divider rule landed through the VEDANSH line and the top-overlaid वेदांश crossed the भक्ति पत्र frame rule. `suvicharFooterBand` and `suvicharBrandSlot` hold per-frame fractions measured on all 42 masters (footer divider ≈ .90/.91, bottom border ≈ .97–.98; blank top space: jharokha cartouche .008–.076, floral band .004–.054, letter-frame margin .004–.064 with its rule at ≈ .03); re-measure if a master is regenerated. Every frame uses the same app-icon + वेदांश pill; anything taller than ~21 dp would cover the crowns painted at the top centre of most masters. The वेदांश text keeps the full 1.65 leading (a 16 dp line box clipped the matras on iOS, shipping as "वदाश") and negative vertical margins keep the pill at 19 dp. The bundled brand mark is part of capture readiness. Daily Bhakti's entry is `SuvicharEntryCard` (miniature card + title + caret), not a bordered text box.

Salasar identity requires a shrine photo reference: the broad orange monolithic form, round eyes, triangular red nose and flat painted moustache/beard are essential. A naturalistic bearded human head was rejected despite matching the descriptive keywords. All three masters were corrected on 23 October; original frames and reviewed paper boundaries remain.

The composer has explicit control tiers (mode segment, underline filter tabs, painted deity/frame tiles, eyebrow labels) and a sticky heart + Share bar; the message is editable in both modes and the sender collapses to a `सप्रेम — name ✎` row once saved (design.md §82 composer layout). Ready-made mode is the default: `suvicharTemplatesFor(day)` in data/suvicharTemplates.ts composes one card per deity and seven wishes from existing authored content; the 21 thoughts rotate across deity cards by local day (stride = rail length, kept coprime), ranked from the day's weekday deities first via `suvicharTodayTemplates(date)` (data/suvicharVaar.ts) so the weekday card cycles all 21 before repeating, and an unedited authored thought is dropped on load so each visit opens on today's thought. SuvicharPresetPicker virtualizes thumbnail subscriptions to the shared R2 cache. A selection updates deity/frame/message while preserving the sender, and the full native SuvicharCard remains the single capture surface. All three frames remain available; custom mode preserves existing editing tools and switching modes does not reset preferences.

Weekday cards (design.md §82 *Suvichar weekday cards*, `data/suvicharVaar.ts`): the day is only in the card title (`SuvicharCard` `title`, replacing the “आज का सुविचार” label), never in the message, which is the deity's thought for the day from `suvicharTodayTemplates` (the same rotation the deity cards use). Gotcha: rank must come from the day's deities, not catalog index; ranking by catalog index (pre-fix) made the weekday card repeat within 8 days and never reach 3 of the 21 thoughts. Only the lead card's 21-day cycle is guaranteed; an alternate deity's rank shifts by weekday. The pool itself is 21 thoughts, so a repeat every 21 days is a content ceiling, not a bug; the 1,000 drafts in docs/content/suvichar are still editorial-review-pending. The ready-made rail's आज tab lists each of the day's deities in all three frames (`suvicharVaarTemplates`). `withTodaysVaar` runs on hydration and when the app returns on a new day: it sets `vaar: true` and an empty message (which renders the deity's thought for today) unless the reader wrote the message, keeping frame, sender and favorites. Favorites store `vaar: true`, not a title, so a restored card names the current day. The Daily Bhakti entry names the day and deity and shows cached art only (`peekBackgroundAsset`, never a download).

Weekday gotchas: `suvicharVaarFor` filters each day's deities by manifest presence, so a newly listed deity stays hidden until its masters are published, and Sunday shows Vishnu and Tirupati as Surya-Narayan until Surya masters exist (Surya then goes first). Every catalog deity is linked to at least one day (a test enforces it): forms follow their deity (Salasar with Hanuman; Tirupati, Jagannath, Ram and Ram Darbar with Vishnu on Thursday; Radha–Krishna, Sanwariya Seth and Khatu Shyam with Krishna on Wednesday, where Saraswati joins Ganesha). Friday is Lakshmi with Durga as alternate, deliberately unlike Routine's `VAAR_DEITY`. Latin titles reuse the weekday hashtag spellings in `shareHashtags.ts` (Mangalwar, Shukrawar). Screen tests fake only `Date` (`jest.useFakeTimers({ now, doNotFake: [...] })`) and pin the old suite to a Sunday; anything that asserts the default tab must pick a date.

Sender photo (design.md §82 *Suvichar sender photo*): an opt-in round photo above “सप्रेम — name”. The section stays hidden behind the `photoOn` switch (off by default); turning it off hides the photo but keeps the file. It is picked via `expo-image-picker` (no manual crop) and fitted to its faces automatically: the local `SuvicharFace` module (Apple Vision on iOS, platform `android.media.FaceDetector` on Android, on-device, no extra deps) returns face boxes, and `suvicharPhotoFit` turns them into the square the circle shows (all faces for a family photo, centred square fallback). The fit (`photoFit`) is applied at draw time by `SuvicharSenderPhoto`, never baked into a cropped file. The photo is copied to `documents/suvichar/sender-<ts>.<ext>`. Preferences keep only the file name (`photo`, `isSenderPhotoName`), never the URI, because the iOS container path changes on update. Favorites do not store it; replacing or removing deletes the old file. It joins the card's decode gate; a decode failure clears the preference. Gotcha: the picker is native, so `utils/suvicharPhoto.ts` probes `ExponentImagePicker` and lazily requires it. The row is hidden on any binary built before the module, so the feature reaches users only with a store build, not OTA. The plugin blocks camera and microphone permissions. Gotcha: the face module's Swift/Kotlin was written without a native build in the authoring container; the first EAS build is its compile check, and a detector failure only drops to the centred square.
