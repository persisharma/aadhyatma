## Summary

The Panchang tab provides a Hindu-calendar almanac: date picker, festival/vrat observances, a katha library, Daily Muhurat, private Pitru Smaran, Kundali, deterministic Daily Rashifal, private Guna Milan, and newborn-private Namkaran. Panchang's top selector has three peer modes: `Panchang | Vrat & Parv | Jyotish`. The Jyotish engines extend the existing astronomy primitives and remain offline and deterministic. Kundali uses an Indian birth city for Lagna; Guna Milan and Namkaran use IST civil birth date/time because their Moon-longitude calculations do not need place. Birth details are a **roster** of people with one active selection, so every personalised surface answers for whoever is chosen.

## Details

**Navigation** (`TabNavigator.tsx`, `PanchangStackNavigator.tsx`): tab 3 root is `PanchangScreen`; `MuhuratDetail`, `Kundali`, `Rashifal`, `GunaMilan`, `Namkaran`, `NamkaranResult`, and `NamkaranRashi` are routes in the same native stack. `PanchangHome` accepts `initialTab`, allowing Home's permanent Kundali launcher to land directly on Jyotish without making the calendar root unreachable. `TabNavigator` loads this stack through `React.lazy` + `Suspense`, so evaluating Panchang/Jyotish modules cannot delay Home's first interactive frame.

**PanchangScreen** (`screens/PanchangScreen.tsx`): the three-way mode selector is the fixed first control, so switching to Jyotish cannot move it; the location/calendar-system/My Vrat row follows only in Panchang and Vrat modes. The screen then provides date picker + month calendar + observance list + katha section + a `MuhuratGlanceCard` row. The Jyotish branch is stateful: guests get Create Kundali, Daily Rashifal, and one Navagraha practice card; saved profiles get a daily-first landing with all three guidance rows, a compact Kundali reference, then the same one practice treatment. Focus refresh after save prevents a stale guest landing. Tapping the glance card navigates to `MuhuratDetail`.

**Location list** (`panchang/locations.ts` + `panchang/rajasthanTehsils.ts`): `CITIES` is `[...MAJOR_CITIES, ...RAJASTHAN_TEHSILS]` — 52 nationwide cities/pilgrimage centres (Ujjain first, because `DEFAULT_LOCATION` is `CITIES[0]`) followed by 342 Rajasthan tehsil headquarters spanning all 33 revenue districts.
- A tehsil is any `City` carrying `districtHi`/`districtEn`; the national tier leaves both undefined, and that field is what the picker partitions the two groups on and what labels the row `<name> · <district>`.
- `cityMatchesQuery(city, q)` is the one search predicate, shared by `LocationPickerModal` and the Kundali birth-city sheet: English name, Hindi name, or district in either script.
- Tehsil coordinates were resolved from the GeoNames gazetteer first, then the All-India Pincode Directory, and gated on the Rajasthan bounding box, the district's own office box, and coordinate uniqueness. 28 tehsils are deliberately absent because no dataset row survived those gates — see the generated file's header. `location.test.ts` pins the gates as invariants.

**Pincode tier** (`panchang/pincodes.ts` + generated `panchang/pincodeData.json`, built by `scripts/build-pincodes.mjs`): a third location tier of 18,466 nationwide pincodes, resolved by exact 6-digit lookup and used to snap GPS fixes. It is **not** part of `CITIES` and is never browsable.
- Built by joining two npm datasets (the only reachable egress): `india-pincode-search` for pincode → state/district/taluka, `pincode-lat-long` for coordinates. 18,581 of 18,777 directory pincodes join (99.0%); gates drop 196 with no geocode, 114 at 0,0, and 1 outside the India bbox.
- Payload is a compact `{districts, talukas, states, statesEn, statesHi, rows}` shape — one flat numeric array, stride 7, pincode-ascending so `lookupPincode` binary-searches it. 700 KB, behind a **lazy `require`** so it never reaches the launch path.
- Labels: `416001 · Kolhapur, Maharashtra` in English, `४१६००१ · महाराष्ट्र` in Hindi. The Hindi half is real Devanagari (digits + one of 36 hand-authored state names), so gu/kn transliteration works through the normal `contentByLang` path. District/taluka stay Latin in every language.
- `snapToNearestLocation` compares the nearest pincode against the nearest bundled city and takes whichever is **actually closer**, ties to the city. `pincodes.test.ts` and `PanchangLocationContext.test.tsx` pin both directions.
- A stored `pin-` location is **self-describing** and validated structurally in `parseStoredLocation` (range-checked labels and coordinates), because the launch path cannot import the table. `pincodePrefs.jest.test.ts` pins the validation.

**Kundali engine** (`panchang/kundali.ts`): pure calculations from an explicit UTC instant and bundled Indian city coordinates.
- Reuses `engine.ts`'s Lahiri ayanamsa; Sun/Moon/classical planets come from `astronomy-engine`, Rahu is the mean ascending node, and Ketu is exactly opposite.
- `computeLagna` solves the eastern ecliptic/horizon intersection and converts it to the sidereal ascendant.
- Houses are whole-sign from the Lagna sign. Each of nine grahas includes sidereal longitude, rashi, degree, nakshatra, pada, house, and retrograde state.
- `computeVimshottariDasha` uses the Moon's nakshatra, canonical nine-lord order, birth balance, and contiguous Mahadasha/Antardasha periods over the 120-year cycle.
- `buildKundaliInsights` explains Lagna, Moon, and current Dasha structurally for newcomers; it does not diagnose personality or promise events.
- `computeRashifal` anchors the India civil day at 06:00 IST, evaluates deterministic transit-house support for any Moon-sign index, and returns Favour/Pause/Practice/Reflection copy plus one allow-listed existing reader id. No random, AI, network, or luck-score path exists.

**Kundali hook/UI**:
- `useKundali.ts` owns the on-device profile `{ name?, date, time, cityId }`, strict input parsing, IST→UTC conversion, AsyncStorage hydration, and explicit loading/guest/saved/error states. Empty and corrupt storage are distinct; save/remove failures propagate to visible recovery UI. Birth city is independent of `PanchangLocationContext`.
- `KundaliScreen` starts with a blank city instead of a default profile. Saved profiles open the result; Edit is the only place removal appears. Results lead with `Overview`, followed by `Chart | Grahas | Dasha`, and every tab change resets the scroll position.
- Overview's Lagna, Moon, and Dasha cards are actionable. Traditional rashi labels are paired with plain-English equivalents, while the requested Lagna/Moon explanation copy avoids personality verdicts.
- `NorthIndianChart` renders the fixed-house diamond with SVG and exposes all twelve houses/occupants in one accessibility label; the Grahas table is the equivalent textual representation.
- The Dasha tab leads with current Mahadasha/Antardasha dates, progress, elapsed/remaining time and a current chip, followed by a connected nine-period timeline. The timing summary is accessible.
- `RashifalScreen` defaults to the saved chart's Moon rashi or allows manual selection across all twelve traditional/plain-English sign pairs. It renders Favour/Pause/Reflect with graha/bhava context, keeps the traditional-guidance disclaimer visible, and routes one suggested practice through the existing reader dispatcher.
- `JyotishGuidanceRows` and `JyotishPracticeCard` keep landing/detail treatments consistent. `JyotishShareSheet` captures a 4:5/1080×1350 `JyotishShareCard`: Kundali warns that name/date/time/city are present, while Rashifal explicitly excludes personal birth details.

**Multi-person roster** (`panchang/birthProfiles.ts` + `panchang/birthProfileStore.ts` + `components/PersonChips.tsx`; design.md §51a, RULEBOOK §14.5): PRD-C stored ONE birth profile, so a shared phone could hold one person's Kundali at a time. Birth details are now `{ activeId, people[] }` under `@vedansh:kundali-profiles:v1` (cap `MAX_PEOPLE` = 8).
- The split mirrors `panchangDayStore` ⇄ `panchangDayCache`: `birthProfiles.ts` is PURE (validate/parse/add/update/remove/select/`activePerson`, ids supplied by the caller) and also the new home of `BirthProfile`, `validateBirthProfile`, `birthProfileToInput` and `parseStoredBirthProfile`, which `useKundali.ts` re-exports so existing importers are untouched. `birthProfileStore.ts` holds AsyncStorage, one in-memory snapshot, a subscriber list and a serialized write queue.
- `useKundali()` keeps its single-profile shape — `profile` IS the active person, `saveProfile`/`clearProfile` act on them — and adds `people`/`activeId`/`canAddPerson`/`selectPerson`/`addPerson`/`updatePerson`/`removePerson`. `useBirthProfileRoster()` is the shared subscription, used by `useMuhuratBala` too, so a person switch reaches the muhurat strip without a focus round trip. Only the ACTIVE person's chart is computed (a roster of eight would otherwise run eight Kundali solves to draw a chip row).
- One-shot migration: a valid record under the PRD-C key `@vedansh:kundali-birth-profile:v1` becomes person one and the legacy key is then REMOVED (otherwise "remove this person" would leave a readable copy of their birth details on disk); an unreadable legacy record is never deleted and still reaches the shipped corrupt-profile recovery state. Both keys are enumerated as non-cache keys in `derivedCacheReset.test.ts`.
- `PersonChips` is the one switcher control (44 pt floor, 1.25 font cap, name or birth date as the label, dashed `+ जोड़ें` chip, English a11y labels `Show Kundali/Jyotish/Rashifal for <label>`). It renders above what it changes on the Kundali screen (every state), the Jyotish landing (above the Rashifal card) and Rashifal (only with 2+ people and no explicit `rashiIndex` route param). Adding is additive — `Kundali { newPerson: true }` opens a BLANK form and the saved people are untouched; removing one of several lands on a survivor, removing the last returns the guest state.
- With more than one person saved, copy that said "your" names the person instead (landing + Rashifal source lines, and `MuhuratBala.personName` → the strip's `<नाम> के लिए`). With exactly one person every string is byte-identical to what shipped.
- Tests: `panchang/__tests__/jest/birthProfiles.jest.test.ts` (model + storage + migration + serialization + failed-write/failed-read), `screens/__tests__/MultiProfileJyotish.test.tsx` (real store against the real screens, incl. a fixture precondition that the two people have DIFFERENT Moon signs), the extended `MuhuratPersonalStrip.test.tsx`; `.maestro/multi-profile-jyotish-smoke.yaml` authored, device run owed.

**Guna Milan** (`panchang/gunaMilan*.ts`, `screens/GunaMilanScreen.tsx`):
- `gunaMilanConvention.ts` is the versioned calculation contract for all eight Ashtakoota tables, score bands, and directional row/column choices; the provenance and supported cancellation rules are pinned in `docs/roadmap/conventions/guna-milan-v1.md`. The B. V. Raman Yoni matrix is directional (bride row, groom column), including asymmetric Horse/Deer and Lion/Buffalo orientations; never symmetrize it.
- `gunaMilan.ts` is pure and calls the existing Lahiri Moon longitude primitive. Inputs are civil date plus time in IST; location is intentionally absent because Moon longitude at a fixed instant is geocentric. An unknown time enumerates every nakshatra/pada/rashi/degree-sensitive Vashya classification crossed during `00:00–23:59:59` IST, then evaluates the Cartesian product. It emits one exact score only when all eight row scores and flags are stable; otherwise it emits a min/max range and varying-koota ids.
- The screen keeps groom/bride as explicit calculation roles and can copy the saved Kundali profile into either role, but copies only name/date/time and never city. Draft persistence is off by default and versioned behind a visible `Remember match details` opt-in/clear control. Draft saves/removals share an invalidating mutation queue, so turning persistence off removes even a write already in flight; never replace this with independent fire-and-forget storage calls. Local diagnostic counters have no birth inputs.
- Exact results expose all eight expandable rows, base score and convention-adjusted interpretation separately. Expanded inputs are localized domain names, never enum keys or zero-based indexes. Range results name each unknown-time role's possible nakshatras and deliberately have no single band or share action. `GunaMilanShareCard` receives a privacy allow-list model containing optional names, roles, scores, band, and disclaimer only.
- `gunaMilan.engine.test.ts` pins every relevant longitude boundary and all 108×108 pada pairs; `gunaMilan.golden.test.ts` checks independently published reports and supported Bhakoot cancellation branches; `GunaMilanExperience.test.tsx` covers both-role autofill, accessibility expansion state, unknown-time range, persistence parsing, local metric serialization, and the share privacy boundary. `.maestro/guna-milan-smoke.yaml` is one platform-neutral flow that must be run and reported independently on iOS and Android.

**Namkaran** (`panchang/namkaran*.ts`, `screens/Namkaran*.tsx`; PRD-17 Phase 1 scaffold):
- `namkaran.ts` is pure and shares Kundali's exported 13°20′ nakshatra / 3°20′ pada spans and Lahiri Moon-longitude primitive. Exact birth time yields one charana; unknown time bisects every charana boundary crossed across the complete IST civil day (including the 107→0 wrap) and renders equal candidate rows—never an assumed noon, rank, hero, or exact-share action.
- The child-mode `BirthDetailsForm` asks only date and optional time: no name, city, saved-Kundali autofill, or Panchang-location mutation. Birth input is session-only unless the initially-off opt-in is selected; its invalidating storage queue makes clear win over an in-flight save. The separate shortlist record contains name ids only.
- Manual browse has three doors. “Choose by nakshatra” uses the shipped Home `CategoryCard variant="launcher"` as a **3-column × 9-row** grid of 27 name-first tiles: the current-language name fits inside over at most two lines, ordinal-number titles are absent, and tile width stays one point below the exact division to avoid iOS sub-pixel wrapping. Selection then shows four full-width `ListCard` pada rows. “Choose by rashi” reuses the identical grid over 12 tiles and lands on `NamkaranRashi`. “Browse all 108” is the explicit long index. Name rows keep the shared `ListCard`, but their 44 pt shortlist buttons are accessible sibling overlays rather than nested accessible controls swallowed by the parent card on iOS.
- Exact results show `NamaksharCard`, a collapsed user-level Lahiri disclosure, lazy corpus-backed names, filters, an id-only shortlist, a 3×3 rashi-sound grid, Namkaran Muhurat navigation, and a 4:5 share model that cannot accept birth fields. Navigation chrome and dense result controls cap their system font multiplier at 1.25 (1.15 for chips) so accessibility text cannot clip through the safe area, cards, or adjacent controls; devotional/reading text remains scalable. The 44 pt shortlist star is a sibling overlay rather than a nested control inside the `ListCard`; selected state uses both fill and tint. Empty filter combinations offer a reset-to-all action, while the approved Ashwini/Chu prototype route has a `Chudamani` row. Name detail remains a bottom sheet and always shows Hindi + English meanings, an attested root/deity link where present, and copies only the candidate name. The corpus import is forbidden from App/Home/root navigation/global search so startup remains independent.
- **Charana is primary; rashi is reachable, not a rival answer.** The charana is the finer cell (1 of 108) and a rashi is exactly 9 of them derived from the same table, so the hero, corpus index, filters, shortlist, muhurat door, and share model all stay charana-keyed. Three gotchas the first implementation hit: (a) the cross-check grid must iterate `rashiCharanaEntries`, **not** `rashiSyllables` — flattening renders 13 cells for Makara, whose Shravana charanas carry the dual ज/ख series, breaking the "nine sounds" 3×3 contract; (b) an unknown-time result must render one card per `distinctRashiIndices(candidates)` — a day covers ≈ 3.6–4.5 charanas against 9 per rashi, so ~1 day in 2 crosses 30° and naming `candidates[0].rashiIndex` alone ranks a candidate the range path forbids ranking; (c) the grid cells are controls, so they carry the 44 pt floor, not the old 40 pt display height; and (d) the cell(s) matching the result's own charana must render as a marked non-interactive `यही · this one` state rather than navigating, or the grid pushes a duplicate of the screen being read. The `NamaksharCard` hero is never tappable (`accessibilityRole="summary"`) — it is the answer, and its names are already in the list below it. Unknown-time `CandidateRow`s **do** open that charana's full result, passing `fromUnknownTime` on the route: that flag (not the basis) shows the "one of the day's possibilities" notice and suppresses the exact share plus its shortlist opt-in, so the range path cannot become a two-tap route to a confident share. The same charana reached through a nakshatra or rashi browse still shares — a table lookup is not a claim about this child's birth. The flag must also travel through `NamkaranRashi` via its `dayCharanas` param: without it, range → rashi detail → tap one of the day's own charanas reopened that candidate as a settled, shareable answer, which is the same hole in a different door. `NamkaranRashiScreen` is the detail — summary card, then the 9 charanas grouped by nakshatra as `ListCard` rows with lazily-counted corpus totals — and is its own route because both the entry door and the result card open it.
- **Not release-ready:** `NAMAKSHAR_SOURCE.verified:false` and the small `NAMKARAN_CORPUS.releaseEligible:false` development shard keep both religious-content gates open. Source access is no longer the issue: the complete DrikPanchang and myPanchang 2019 108-pada tables, Sanjay Rath's Gana table, and an academic deity cross-check are now pinned. Human review still must settle short/long-vowel spellings, Purva Ashadha pada 4 and the Shravana ja/kha regional variant, and the corpus still lacks the required attested 12+12 names per charana. Tests and the release gate prevent the scaffold from masquerading as complete; automation passing does not authorize release exposure.
- Tests cover boundary/purity/state/corpus/screen behavior. `.maestro/namkaran-smoke.yaml` passed on a fresh iPhone 17 Pro Max simulator (iOS 26.5) on 2026-08-13; Android remains a separately required run.

**Muhurat engine** (`panchang/muhurat.ts`): pure arithmetic — no React, no astronomy, no `Date.now()`.
- Inputs: `sunrise: Date, sunset: Date, nextSunrise: Date, weekday: number`.
- Output `MuhuratDay`:
  - `dayChoghadiya[8]` + `nightChoghadiya[8]` — equal eighths of day/night; the 7-key WHEEL cycles from a weekday-specific start index (day) and `+5` offset (night). Convention: DrikPanchang.
  - `rahu`, `gulika`, `yamaganda` — fixed weekday-indexed eighths of the daytime (`RAHU_SEG`, `GULIKA_SEG`, `YAMAGANDA_SEG` tables).
  - `abhijit` — the 8th of 15 equal day-muhurtas (≈ solar noon); `null` if the day duration collapses.
- `classifyNow(md, at)` — point query returning current choghadiya + kaal for a given timestamp.

**Display helpers** (`panchang/muhuratFormat.ts`): `formatClock(d)` → 12-hour AM/PM string; `formatRange(a, b)` → range string; `formatRangeCompact(a, b)` → range with a shared meridiem written once (`3:37 – 5:13 PM`, full form across noon/midnight — the Home Today strip's chips); `formatEndInstant` → end clock with a short-date suffix on day-crossing. All pure.

**Hook** (`panchang/useMuhurat.ts`): bridges the shared day-store with the live clock, and — on a today surface — rolls the persisted window a week forward once the day's own solve has landed. It owns NO cache — the three panchang solves it needs (today, tomorrow, and yesterday for the pre-dawn correction) come from `panchangDayStore` and are persisted, so Home's Today strip and the daily Muhurat card no longer re-solve on a cold start and share days with the finder's sweep. `MuhuratDay`/`nowPeriods` are re-derived per call (pure arithmetic over the cached days).
- Defers both `computePanchangForDate` calls (today + tomorrow) until `InteractionManager.runAfterInteractions`, then yields once more via `setTimeout(0)` — Home remains responsive while an initial scroll/tap is in progress and the hook returns `null` until the solve finishes. `useObservancesForDate` follows the same interaction-aware scheduling boundary.
- `useMinuteTick()` drives the live "now" recalc without re-solving the astronomy.
- Pre-dawn correction: when `isToday` and the clock is before today's sunrise, yesterday's night choghadiya window is prepended to `nowPeriods` so the active choghadiya resolves correctly.
- Returns `{ muhurat, panchang, isToday, nowChoghadiya, nowKaal }`.

**UI components**:
- `TodayStrip` — Home's lightweight Panchang glance. Its chip ScrollView always reserves the solved-row height, including while data is `null`, so deferred observance/muhurat results cannot move the category grid under a finger.
- `MuhuratGlanceCard` — inline summary on PanchangScreen (today's/selected Rahu Kaal + current choghadiya quality pill).
- `MuhuratCardBody` — shared body rendering the full 8+8 choghadiya table + three kaal rows; used by both glance card and detail screen.
- `MuhuratDetailScreen` — full-page view; sharing via `expo-sharing` + `react-native-view-shot` (captures a `View` ref). `busy` flag prevents double-taps.
- `ObservanceDetailHero` and `ObservanceListRow` — quiet observance primitives shared by Vrat/Parv and Pitru Smaran. They expose presentational slots but keep domain copy and actions in each screen. Do not replace Pitru rows with the Muhurat discovery `ListCard`; its gradient, thumbnail, elevation, and chevron encode a different interaction.
- Pitru Smaran is a device-only ledger with four standing/contextual touchpoints: the More management flow, an always-visible pinned row under My Vrat in the Vrat/Parv catalog, a zero-state Home DISCOVER card, and public/private chips on Home Today and the Panchang day panel. Private chips match both the saved annual tithi and the person's mapped Pitru-Paksha day. The person detail, Pitru-Paksha overview, and public Sarvapitri chip now open the narrow `shraddha-tarpan-vidhi`; only `{vidhiId, dateMs}` crosses the route, never a family name, relation or ledger id. Public season reminders follow the festive preference and never name family; a deliberately saved new person defaults their day-before/day-of reminder on after the shared OS grant succeeds, while denied and legacy-omitted preferences remain off.
- `PanchangTimelineRow` — marker/date/title timeline shared by Panchang Upcoming and Pitru Paksha. Its compact and comfortable densities preserve the original layouts; Pitru can add one or more family-name lines.

A tithi lasts 19h59m–26h47m, so between consecutive sunrises the index advances by 1 (normal), 0 (**vriddhi** — same anga at two sunrises), or 2 (**kshaya** — the anga begins and ends strictly inside the day, touching no sunrise; kshaya tithis occur roughly monthly, kshaya nakshatras similarly). `computePanchangForDate` detects the +2 jump against the next day's sunrise (memoised in `sunriseCache`, shared with all solvers) and fills `PanchangData.kshayaTithi` / `kshayaNakshatra`; UI shows them as a second row on the Tithi/Nakshatra tiles and as `क्षय` rows on the Muhurat card, with `formatEndInstant` (muhuratFormat.ts) adding a short-date suffix for past-midnight ends. ## Gotchas

- **A pitru answer cache is keyed by TITHI, never by person — and by nothing else either.** Three traps sit in `pitruSmaranSolves.ts`. ① The record key is `m11-krishna-8`, not the entry id: the ledger is private, two people on one tithi genuinely share an answer, and an entry-keyed cache would be both worse and a disclosure. Its prefix `@vedansh:pitru-solves:` is one character from the user-authored `@vedansh/pitru-smaran` and sits on the OPPOSITE side of the derived-cache sweep — `pitruSmaranSolves.jest.test.ts` pins both halves. ② The keys carry **no location/system scope**, because every Pitru surface solves at the engine default (Ujjain/purnimant) — the feature deliberately does not follow `PanchangLocationContext`, since a shraddha tithi does not move with the user's city. Thread a location option through those screens and this cache must gain a scope segment first, or one city's answers get served for another. ③ A **miss must be remembered too**: without the negative-cache set, a device that has never solved anything — every first-ever entry to the feature — repeats the whole `multiGet` on each screen, which is the same "disk round trip in front of a screen that could already paint" the panchang gotchas above are about. Safe, because a key absent from disk can only become present via this same process, which puts it in memory too.
- **The detail screen's hero pill must not wait on the rows below it.** All four solves used to land in ONE `setSolved`, so the `अगला` pill — the answer people open the screen for — waited on next year's occurrence, a ~259 ms scan of a date further down the page. It is published in two stages now, in reading order. Two things to preserve if you touch it: an on-demand solve asks for exactly the two dates rendered (the third-occurrence rollover margin is bought by the list's prewarm on idle time, never on the detail's critical path — `KEPT_OCCURRENCES` is the prewarm depth, not the on-demand depth), and the hydrate must start immediately while only the SOLVE waits on `InteractionManager` — the same split `useMuhurat` learned.
- **`primePitruPakshaWindow` never overwrites a year already solved this session.** The persistence layer seeds the engine's own `windowCache` on hydrate, because `pakshaShraddhaDay` and `entryMatchesDate` reach that memo directly rather than through the cache — seed nothing and the disk read buys those callers nothing. But a seed arriving after a real solve must be ignored: callers may already hold the `Date` instances the memo handed out. Pinned in the tsx suite, which also asserts seeded == fresh for a rule mapped into the fortnight.
- **Do not fast-forward an annual tithi scan by ~345 days.** The obvious optimisation for "the occurrence after this one" — skip the ~11 lunations that cannot contain it — is WRONG: a swept comparison over 24 rules × 8 years found 12 real 29-day gaps, all `krishna` pratipada, where the rule fires in both the adhik and the nija month of an adhik-maas year. The measured gap range is 29–385 days, so no safe blanket stride exists. Caching the answer is the correct fix; changing the scan's semantics for speed is not.
- **Regenerate the precomputed observance table after any matching change** — `TZ=Asia/Kolkata npx tsx scripts/gen-precomputed-observances.mts` (from `mobile/`); the app reads `precomputedObservances.ts` for Ujjain, so an engine fix that isn't regenerated never reaches users for 2024–2031.
- **Bump `CACHE_VERSION` in `observanceCache.ts` with every such change** — non-Ujjain cities persist their scans to AsyncStorage keyed by version; without the bump, previously-scanned devices hydrate the old dates forever and never re-run the scan (the fix ships only to Ujjain and fresh installs).

- **Bump `PANCHANG_DAY_CACHE_VERSION` (`panchangDaySerde.ts`) with every panchang-engine change** — the finder's per-day solves are persisted per (location, calendar system) and hydrated on entry. Without the bump, a device that already scanned keeps serving the OLD engine's days forever and the fix reaches only fresh installs. Same trap as `observanceCache`'s `CACHE_VERSION`, one layer down (that one guards *matching*; this one guards the *solve*). Adding a city needs no bump. `dayCacheParity.e2e.test.ts` pins fresh == cached == serialize→revive over a year × 3 locations × 2 systems.
- **`getUpcomingObservances` caps by observance COUNT, not by date** — `.slice(0, count)` runs AFTER the `withinDays` filter. `scanAbujhDays` passed 60, so from mid-Aug 2026 the abujh list stopped at the 60th observance (26 Oct) and **five of six `ABUJH_RULE_IDS` never rendered** — Akshaya Tritiya, Vasant Panchami, Dhanteras, Akshaya Navami and Dev Uthani Ekadashi were invisible for all of Phase 1, leaving only Dussehra plus the computed Pushya days. Pass an unbounded count and let `withinDays` bound it; `abujhCoverage.test.ts` asserts the scan reaches past its 60th observance.
- **अबूझ days must not be graded by rules the Abujh screen says don't apply.** `evaluateDay(..., { abujh: true })` drops the seasonal doshas (chaturmas, guru/shukra asta). It is a NARROW reading and only partly closes the contradiction: per-day doshas (rikta, panchak) and the nakshatra/tithi/vara factor match still exclude most abujh×occasion pairs, so the app can still say "auspicious in its entirety" on one screen and "not suitable" on the other. Deliberate, documented, and carried to the §10 review (RULEBOOK §17.8) rather than silently widened.
- **A muhurat follow must NEVER store its window.** Every window is sunrise-derived, so a stored time lies the moment the user changes city. The scheduler re-derives from `panchangDayStore` each pass and re-arms on **location and calendar-system change**, not only on follows changing — pinned by `MuhuratReminderScheduler.test.tsx`, which asserts the day-of notice MOVES between Ujjain and Bengaluru while the 18:00 advance notice does not. Three siblings of the same rule: prune past follows or the ★ count counts notices that can never fire; a followed day that re-grades to `excluded` schedules nothing and says so in words (§12); and `clampDayOf` pulls the day-of notice back to `windowStart − 30 min` whatever the user picked, because the shipped 07:00 vrat default arrives AFTER an early-Amrit window (17 Aug 2026 Vahan opens 6:07 AM).
- **Home now reaches `PanchangLocationContext` transitively** (TodayStrip / TodayRecommendationsRow → `useMuhuratFinder`), which drags in `expo-location` — untranspiled ESM that Jest cannot parse. It is mocked globally in `jest.setup.js` beside `expo-speech`; without that, two shipped component suites fail to even load.
- **The FOR TODAY abujh card must not lead on a catalogued festival day.** `festiveReminders.test.ts` asserts the row leads with the festival card on those 18 days, so the abujh card slots second there and leads only otherwise (Guru/Ravi Pushya, the common case). It rides the ROW, not `getTodayRecommendationDetails` — that function stays `LibraryEntry`-only so the notification ⇄ FOR TODAY contract is untouched.
- **Do not add a private panchang cache to a hook or screen** — everything goes through `panchangDayStore`. `useMuhurat` had a per-session, cityId-keyed `SOLVE_CACHE` and the finder had an index-keyed `DAY_INPUT_CACHE`; both were invisible to the other surfaces, neither survived a launch, and the index-keyed one silently missed after a midnight rollover. Both were deleted.
- **The widget writer is the one surface that must NOT use the store** — `widgets/planPayload.ts` solves with `civilTimeZone: WIDGET_TIME_ZONE` (its 14-day snapshot is IST-anchored, not device-local), while the scope key models only (location, calendar system). Routing it through the store would alias its days onto the app's. `ScanOptions` declares `civilTimeZone?: never` so this is a compile error, not a silent bug.
- **A store update or OTA now clears the derived caches — and the allowlist is the whole safety story** (`utils/derivedCacheReset.ts`, fingerprint in `utils/buildFingerprint.ts`). Hand-maintained cache versions only invalidate what someone remembered to bump, so this is the backstop: fingerprint = OTA `updateId` · `runtimeVersion` · the bundle's version · the native build number (that last part is what catches a rebuild of the *same* version, which the other three share under the `appVersion` policy). Three traps. ① **Only engine-computed calendar output may be swept** — `panchang-days:` (day solves), the legacy `muhurat-days:`, and `observances:` (festival/vrat dates). Derived state that is not calendar output stays out, e.g. the widget's write-dedupe key: `WidgetCoordinator` re-plans every pass and rewrites whenever the payload really changed, so sweeping it would buy nothing. `@vedansh:panchang-location` and `panchang-calendar-system` look panchang-shaped and are NOT caches: sweeping them silently returns the user to Ujjain. Nor is `notif-meta` (it mirrors what is actually scheduled with the OS), nor any follow/count/bookmark/birth-detail/Pitru-Smaran key. `derivedCacheReset.test.ts` enumerates the real non-cache key set and fails if a prefix ever starts matching one. ② **The gate is what makes it correct** — `App.tsx` registers the reset at *module scope* and both caches `await awaitDerivedCacheReset()` before storage, on hydrate (don't read what the sweep will delete) *and* on persist (don't write what it will wipe while `known` claims those days are on disk). ③ **`expo-updates`/`expo-constants` must stay out of the cache graph** — untranspiled ESM Jest cannot parse, so the reset module imports AsyncStorage only and takes the fingerprint as a plain string; importing them into a cache module breaks ~90 suites, the same trap as `expo-location` reaching Home. A bump of `PANCHANG_DAY_CACHE_VERSION` is still required — this fires only when the *build* moves, so within a release the version is still the only invalidator.
- **Never call through a spied AsyncStorage method** — every method on the official jest mock is already a `jest.fn`, so `jest.spyOn` hands back that SAME fn; a saved reference (`AsyncStorage.multiRemove.bind(...)`) then invokes the *new* implementation and a call-through recurses until the suite dies. To observe ordering, stall a different method with a deferred instead (see `derivedCacheReset.test.ts`). Same root cause as the call-count bleed the panchang cache suite documents.
- **A persisted window that ENDS where a surface reads is cold again every midnight** — the sibling of the retention gotcha below, on the future side, and the one that produced the "today's panchang is still computed every day" report (Aug 2026). Home reads three civil days (yesterday's night window, today, tomorrow's sunrise) and persisted exactly those three, so the window always ended at tomorrow; the first launch after each midnight found its own "tomorrow" missing, and `composeSolved` returns null on ANY miss — so the Today strip dropped to its `—` headline while the deferred path ran a whole-keyspace purge, a `multiGet` and a fresh solve. Every day, forever. Persistence was not broken; its window was one day too short. `panchangDayPrewarm.ts` now rolls the window `PREWARM_DAYS` = 7 past today after the day's own solve lands (same reach as `FOLLOW_CHIP_HORIZON_DAYS`, so the strip's follow chip lands warm too). Two traps if you touch it: the warm must run AFTER the render solve (ahead of it, the extra days delay first paint), and it must not feed React state. Pinned by `panchangDayPrewarm.jest.test.ts` and the rollover case in `panchangDayRouting.jest.test.ts`.
- **A cache HIT is only fast if the read is allowed to START early** — the third and final shape of the same report ("still slower than the homepage", Aug 2026), and the one the two fixes below could not reach: not what stood in front of the read, but *when it began*. The scope key needs BOTH panchang preferences, and they were read separately — the city from `PanchangLocationProvider`'s effect, the calendar system **lazily by its first subscriber**, which is Home's Today strip, mounted only after `AppReadyGate` opens the splash on the font-scale/language reads. So the `multiGet` answering "what is today's panchang" was the launch's THIRD serial storage round trip, behind a screen that had already painted everything else from bundled JS. `panchangPrefs.ts` now owns both preferences behind ONE memoized `multiGet` (they are read together because together they ARE the scope key), and `panchangLaunchPrefetch.ts` turns that into warm days from `App.tsx` **module scope** — concurrently with the splash gate rather than after it. `PanchangLocationProvider` and the calendar-system store both seed from that one read (the provider issues no storage call of its own and starts on the user's real city with `isLoading` already false), so `useMuhurat`'s cache-only `useState` seed composes on the FIRST render. Four traps if you touch it: ① the prefetch is **hydrate-only and must never solve** — moving I/O earlier must not drag CPU onto the launch path, which is exactly what the `InteractionManager` gate exists to prevent; ② it must warm exactly `todayMuhuratDayKeys()`, the shared helper `useMuhurat` reads through — `composeSolved` returns null on ANY miss, so warming a different set is indistinguishable from warming nothing; ③ `panchangPrefs` may import only AsyncStorage + `locations.ts`, because it is imported by BOTH `PanchangLocationContext` (which pulls in `expo-location`) and the prefetch (which must not) — same isolation rule as `expo-updates` and the cache graph; ④ the memoized read must be cleared between Jest tests (`__resetPanchangPrefsForTests`), or every case is served the first case's storage; ⑤ only a SUCCESSFUL read may be memoized — the calendar-system read used to clear its own promise on error so the next subscriber retried, and consolidating two reads into one is exactly where that guarantee gets dropped: without it a single transient storage failure at launch pins the whole session to Ujjain + purnimant with no path back until the app is killed. A failed read also seeds no snapshot, so the provider still mounts in its loading state rather than presenting the fallback city as a settled answer. Pinned by `panchangLaunchPrefetch.jest.test.ts`, including a deliberate non-vacuity case asserting the first render IS blank without the prefetch.
- **A cache HIT is only fast if nothing stands in front of the read** — the sibling report to the one above ("still not reading from cache", Aug 2026): persistence and the roll-forward were both working, and the strip *still* sat on `—` at every cold start, because three things were queued ahead of a `multiGet` that answers in one round trip. ① `useMuhurat` ran its whole chain behind ONE `runAfterInteractions` + `setTimeout(0)`, so disk I/O — which the JS thread does not perform — waited for an idle UI it did not need. Hydrate now starts immediately and paints the moment disk answers; the interaction gate is reserved for astronomy on days disk did NOT have, and for the roll-forward. ② `TodayStrip`'s chip auto-scroll never declared `isInteraction: false`, which defaults to `!useNativeDriver` — and that loop *cannot* use the native driver, since it drives `scrollTo` from a JS listener. So an endless decorative animation held an InteractionManager handle and "idle" almost never arrived on Home, starving the observance chips, the pitru match, the muhurat/festive schedulers, the widget writer and the strip's own rollover. Its end pauses are no-op `timing` holds, because `Animated.delay` takes no config and would keep claiming a handle. ③ `purgeUnusable`'s whole-keyspace `getAllKeys` + `multiRemove` ran BEFORE the `multiGet`; it is pure housekeeping (a stale-version key is under a different prefix and can never be returned by a current-prefix read; a still-readable day past retention is a correct solve for that day) and now runs after, unawaited — `panchangDayCacheSwept()` is for the cache's own tests only.
- **Neither daily surface may work on a placeholder scope** — `usePanchangLocation` reports `DEFAULT_LOCATION` (Ujjain) and `usePanchangCalendarSystem` reports `purnimant` for one AsyncStorage round trip at every launch, because React needs a synchronous initial value and the user's choice arrives from disk. A user on any other city, or on amanta, was therefore spending a hydrate, three solves and a seven-day roll-forward on a scope discarded a tick later — on the launch path, in front of the real one. `useMuhurat` gates on `isLoading` + `usePanchangCalendarHydrated()`, the pair `WidgetCoordinator` has always gated on. Do not "fix" this by seeding the provider from the stored city: that read cannot be synchronous without a sync storage engine (MMKV), and the gate is the cheap answer.
- **A test that counts engine calls must scope them to the days a surface RENDERS** — once the roll-forward exists, `expect(solveSpy).not.toHaveBeenCalled()` conflates "Home re-solved what it shows" (the bug) with "the window slid one day out in the background" (the fix). The routing suite filters by date key (`renderedSolves`) instead. Its rollover test also has to cross a midnight, so it fakes **`Date` alone** via jest's `doNotFake` — faking timers too would deadlock the hooks' `setTimeout`-based deferred chain. Maestro cannot express this gate at all (a flow cannot move the device clock), which is why the day-cache smoke only covers cold-start hydration.
- **Persisted retention reaches into the PAST, not just today onward** (`RETAINED_PAST_DAYS` = 2 in `panchangDayCache.ts`) — `useMuhurat`'s pre-dawn correction reads yesterday's night choghadiya, so a today-onward cutoff left Home solving one day on every cold start. Caught by the routing test counting engine calls, not by inspection: the surface still rendered correctly. The second day back is margin for the Panchang date picker. Persist and purge share one cutoff (`oldestUsefulDateKey`) — if they ever diverge, the purge sweep deletes what persist just wrote and every launch re-solves.
- **The day store hands out SHARED `PanchangData` instances** — a consumer that mutates `p` corrupts every other reader of that day (and the persisted copy). Keep reads immutable, or clone before mutating; this is the precondition for routing `useMuhurat`/`usePanchang` through the same store.
- **`panchangDayStore` / `panchangDaySerde` / `muhuratFinderScan` must stay RN-free** — AsyncStorage and react live only in `panchangDayCache.ts` and the hooks, so `tsx --test` can import the engine side. A Jest suite for the cache therefore lives in `src/panchang/__tests__/jest/`: `npm run test:engine` globs `__tests__/*.test.ts` straight into `tsx --test`, which cannot run Jest files.
- **`test:engine` runs under `TZ=Asia/Kolkata`** — the parity sweep asserts Delhi sunrises across a full year, and on a UTC machine a Delhi civil day near the July solstice contains no sunrise, so `computeSunrise` throws. The suite pins the audience's civil timezone instead of the developer's.

- **A `City.id` is a persisted key, never a display string** — it is written to `@vedansh:panchang-location`, to the Kundali birth profile, and into `observanceCache` keys. Renaming `rj-rajgarh-alwar` silently resets a user's chosen location to Ujjain and orphans their cached observance year. Adding entries is free; renaming is not. Tehsil ids are `rj-<slug>`, plus `-<district>` only where the bare slug repeats (Rajgarh, Ramgarh, Shahpura, Kishangarh…).
- **Adding cities does NOT need a `CACHE_VERSION` bump** — the version guards *matching* changes, and a new city has no prior cached scan to invalidate. Bump it only when the festival/tithi logic moves.
- **Don't "fix" a missing Rajasthan tehsil by inventing a coordinate** — 28 are absent because the gazetteer and the postal directory either had no row or disagreed (some postal rows are geocoded onto a same-named town 500 km away, and a few snap several tehsils onto one point). A wrong coordinate is worse than an absent row: the user gets another district's sunrise under their own town's name. `location.test.ts` fails on out-of-state coordinates and on any two tehsils sharing a point.
- **Any picker over this list must virtualize** — the Kundali birth-city sheet was a `ScrollView` + `.map()`, which mounted all ~390 rows and stalled the sheet open. Both pickers are `FlatList` now.
- **Never make GPS prefer a pincode unconditionally** — the geocoder's coverage is wildly uneven: 1 of 207 Jammu & Kashmir pincodes, 19 of 48 in Arunachal Pradesh. A Srinagar fix finds its nearest pincode **156 km away in Doda**, while the bundled `srinagar` city sits on top of it. `snapToNearestLocation` therefore compares both tiers by distance; removing that guard is a silent, state-sized regression that no "does the pincode resolve" test would catch.
- **Pincodes cannot become `City` rows** — a `City` must carry a Devanagari `nameHi` (`location.test.ts` asserts it), neither source dataset has Hindi place names, and `utils/transliterate.ts` runs Devanagari→gu/kn, *not* Latin→Devanagari. Machine-transliterating 18k names would ship plausible-but-wrong spellings. This is why the tier labels itself with Devanagari digits + state instead.
- **Don't statically import `pincodeData.json`** — 700 KB parsed at launch. `pincodes.ts` requires it lazily and `panchangPrefs` imports only the `isPincodeCityId` regex from that module, never the table. This is the same launch-path discipline #268/#269/#272 established.
- **The pincode directory is vintage** — it spells Chhattisgarh "CHATTISGARH" and Puducherry "PONDICHERRY" (mapped to current names on output), and predates the 2019 J&K split, so Ladakh pincodes carry correct coordinates under a stale state label. Coordinates are what feed sunrise, so this is cosmetic.

- **Engine is pure; hook is not** — all astronomy and clock calls live in `useMuhurat.ts`. Never add `Date.now()` or astronomy imports to `muhurat.ts`.
- **Kundali engine is pure; UI supplies time** — `kundali.ts` takes explicit dates and coordinates. AsyncStorage, `new Date()` for “today”, and React belong in hooks/screens. The source-purity test pins this boundary.
- **Golden fixtures are independent** — values in both Kundali Swiss fixtures are Swiss Ephemeris/Lahiri references, not captured outputs from this engine. Regenerate the 150-case corpus only with `scripts/generate-kundali-swiss-corpus.py` and its pinned official files; do not “fix” a failure by copying current app output or widening a tolerance.
- **There is exactly ONE "current person", and it lives in `birthProfileStore`** — the Kundali result, the Jyotish landing, Daily Rashifal and the muhurat आपके लिए strip all read the same active selection, so a switch anywhere is true everywhere on the same render. A screen-local "selected person" would re-create, one layer up, precisely the bug `panchangDayStore` exists to prevent. Two sub-traps the first implementation hit: (a) a failed READ publishes `hydrated: true` (so a surface shows recovery instead of spinning), which means `hydrated` alone cannot gate the retry — without the separate `lastReadFailed` flag one transient storage error pins the whole session to an empty roster with no path back, exactly the `panchangPrefs` lesson; and (b) `saveActivePerson`/`removeActivePerson` must resolve "who is active" INSIDE the write queue, or a read-then-write can save into a person another surface just removed.
- **Removing a person must remove their birth details, which is why the legacy key is deleted on migration** — leaving `@vedansh:kundali-birth-profile:v1` in place after seeding the roster would keep a readable copy of person one's date/time/city forever, surviving their removal. The one record never deleted is an UNREADABLE legacy one: we do not destroy what we could not read, and it is what keeps the shipped corrupt-profile recovery state reachable on an upgrading device.
- **`useKundali`'s single-profile shape is load-bearing** — `profile`/`saveProfile`/`clearProfile` still mean "the active person", so Guna Milan autofill and every other existing caller compiled unchanged. Adding fields is safe; changing those three names is not (and the two suites that MOCK the hook, `KundaliExperience` and `GunaMilanExperience`, must be extended when the shape grows or they render `undefined.length`).
- **A one-person roster must be indistinguishable from the shipped single profile** — the switcher hides, and every "your Kundali"/"आपके लिए" string stays exactly as it was. The naming variants are gated on `people.length > 1` AND a non-empty name, never on the roster's existence, so the solo experience cannot regress into "For undefined".
- **Birth city is not current location** — never bind Kundali input to `PanchangLocationContext`; a user's birth place and present Panchang city are separate domain values.
- **No implicit profile/city** — an empty store must remain a guest state with no preselected rashi or city. Do not hide AsyncStorage failures by rendering a successful result.
- **Saved landing is daily-first** — Daily Rashifal precedes the compact Kundali because the chart is reference material while Rashifal is the repeat-daily action. Keep all three guidance rows on the landing.
- **Sharing has different privacy boundaries** — Kundali includes personal birth fields and must warn; Rashifal must never include them. Neither share card may introduce colours outside the existing theme language.
- **The share card's height is pinned, so nothing inside it may be sized off width alone** — `JyotishShareCard` is `aspectRatio` 4:5 with `overflow: 'hidden'` on a width of `min(334, screenWidth - 2 × spacing.xxl)` (334 on a 393 dp phone, **312 on a 360 dp Android**), while everything stacked in it is fixed-point-size type that does not scale. The Kundali diagram therefore takes the *leftover* height (`kundaliChartSize()` = content height − a 196 dp chrome budget, capped at the historic `min(208, width × 0.61)`). The old `width × 0.61` overran the box below ~334 dp and the `marginTop: 'auto'` method footer — last in the column — was clipped away. If you add anything to this card, raise `KUNDALI_CHROME_HEIGHT` with it.
- **10 pt micro lines need ≥ 1.4× leading and a face that has the script** — three lines in `JyotishShareCard` shipped at `lineHeight === fontSize` (10/10), which slices the top off the line: the header rendered `जन्म कुंडली` as "जन्म कुंडला" and the method footer lost its shirorekha (reported August 2026). The header meta also named Inter, which has no Indic glyphs, so its real metrics came from an unpredictable OS fallback — micro chrome that can carry Indic goes through `pillTextStyle`/`scriptTitleFont`. Same trap as the Panchang calendar `dateTag`; design.md §3.0 now states both halves, and `components/__tests__/jyotishShareCardFit.test.tsx` pins them for all four languages.
- **A large Devanagari line must not pin its `lineHeight` at all** — `NamaksharCard`'s hero shipped 58/78 and `NamkaranShareCard`'s 54/70, both just under the natural line box, so the top of an above-shirorekha matra was sliced off (`के` read as `क` plus a stub, August 2026). A fixed leading is also frozen while the font scales, so it clips again at `maxFontSizeMultiplier`. Give the *container* a `minHeight` and let the line measure itself. Same §3.0 incident family as the Jyotish share card's 10/10 micro lines — and the same fix list applies to the labels around it: five Namkaran micro labels were Inter + Latin tracking (no Indic glyphs, split shirorekha) until they were routed through `pillTextStyle`. `namkaranTypeFit.test.tsx` pins both halves for hi/en/gu/kn.
- **A calendar column must never be a `100 / 7` percentage width inside a wrapping row** — reported August 2026 as "today is 15 August, a Saturday, but the app shows Tuesday". Nothing was wrong with the engine: `computePanchangForDate`'s vara and `buildCalendarMonth`'s cell order were both correct. Both calendars rendered all 42 cells into ONE `flexWrap: 'wrap'` row and let `width: ${100 / 7}%` produce the columns, and **Yoga resolves percentage widths in 32-bit float** — `Math.fround(100/7)` is `14.285714149…`, and `fround(fround(inner × that) × 0.01) × 7` lands just ABOVE the container on some widths (320.000008 pt inside 320 pt). Yoga's line-break test is a bare `>`, so the seventh cell wrapped: six columns laid out under a seven-column header (the header row has no `flexWrap`, so it kept all seven), and every date slid off its weekday. 15 Aug 2026 is grid index 20; `20 % 6 == 2` → column 2 → मंगलवार. It is **width-dependent, which is why it looks intermittent**: verified against the real Yoga (`yoga-layout`), the Panchang month grid broke at 390 and 411 dp (iPhone 12/13/14/16e) and the birth-date picker at 375 dp (iPhone SE/mini), while 360/393/412/428 were fine. Fix: `calendarWeeks()` chunks the month into six rows of seven and the cells are `flex: 1`, so the column count is structural at any width (checked 200–600 dp). Same root cause as the Namkaran 3-column tile grid, which floors `Dimensions.get('window').width` division instead — either shape works; a raw percentage inside a wrapping row does not. Pinned by `calendarGrid.test.ts` (column index == `getDay()` for 96 months, plus a source guard on both files) and two `CalendarDatePicker.test.tsx` cases.
- **Never put `adjustsFontSizeToFit` on a multi-line label with a fixed `lineHeight`** — the 27-tile Namkaran nakshatra grid (`CategoryCard` `launcherLabelPosition="tile"`) did, and on iOS scattered tiles (हस्त · चित्रा · स्वाती) rendered at a few points beside full-size neighbours, well past the declared `minimumFontScale` of 0.8 (reported August 2026). The platform shrink loop is unreliable in that combination and the failure is per-node, so identical tiles disagree. Size such labels deterministically instead — a fixed size plus `numberOfLines` and a `maxFontSizeMultiplier` cap — and verify the widest string fits at the widest multiplier. `NamkaranExperience.test.tsx` pins one uniform size across all 27 tiles.
- **The Rashifal card has no such slack yet** — its chrome is entirely fixed-height (three `minHeight` guidance rows + practice + disclaimer ≈ 375 dp), so it fits at 334 but is tight on ≤ 360 dp phones. Known gap, recorded in design.md §51; treat the row block the same way before trusting that card on small screens.
- **Rashifal is guidance** — do not add deterministic predictions, random/AI copy, remote feeds, professional directives, or devotional content ids outside the allow-list without an explicit product/content review.
- **Two astronomy solves per view** — both today and tomorrow are computed to get `nextSunrise`. Both wait for active interactions and then run in `setTimeout(0)`; the screen shows a skeleton/`null` until they complete. Do not move Home's Today-strip solves back onto the render path.
- **Pre-dawn correction is `isToday`-only** — the yesterday-night prepend only happens when `isToday` is true; when browsing past/future dates `nowPeriods` = today's windows only, so `nowChoghadiya`/`nowKaal` return null for non-today views.
- **Polar-latitude guard** — if `sunset ≤ sunrise` or `nextSunrise ≤ sunset`, `useMuhurat` returns `null` silently; the UI shows a skeleton indefinitely. Unlikely in practice given the location list is curated.
- **Char choghadiya = auspicious** — DrikPanchang marks "Char" as auspicious (movable/good for travel). Some sources mark it neutral. The engine follows DrikPanchang explicitly.
- **An absent उपवास विधि section still means the attached entry is unavailable, not that the UI failed.** `getUpvasInfo` returns null for `status:'draft'` entries by design. All eight v1 entries were source-reviewed and moved to `verified` on 2026-08-19, but future draft entries must remain indistinguishable from no entry until the two-source gate clears; never expose a draft through a placeholder or status flip.
- **The computed parana line is derived display, never data** — it re-derives per render from `panchangDayStore` (persisting it would lie after a city change, the muhurat-follow rule), takes the RESOLVED occurrence from `getNextOccurrence` + 1 day rather than re-matching tithis (the kshaya rule above), and `deriveUpvasParana` returns null on every branch it cannot compute honestly — so the verified rule TEXT must always render on its own, and a null here is a correct state, not a loading failure.
