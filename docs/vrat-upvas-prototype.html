Design decisions — frame A

  • Position preserved: the section renders last, exactly where the parent PRD reserved the "How to observe" slot (§6.2). Hero, actions, About, and Story are the shipped screen, untouched.
  • Fast-type chip is the panel's headline: a filled saffron pill (pillTextStyle, Devanagari-safe leading, 1.15 font-scale cap) with a one-line note beside it — the two facts a devotee scans first.
  • Two labelled rows (उपवास काल · पारण) reuse the app's quiet fact-panel language (Pitru detail's annual-answer rows) — non-interactive, no chevron: actions live in the action row above.
  • Parana is text-canonical: the verified rule sentence always renders. The gold-tint computed line beneath it is derived display — parana-day sunrise → Dwadashi end from panchangDayStore at the user's real location (the shipped P4 location half is what makes this line honest). When derivation returns null (Dwadashi ends pre-sunrise, etc.) the line simply doesn't render — never an invented time.
  • Strictness footnote is transcribed from sources (traditional exemptions), italic-muted so it reads as a note, not a rule row.
All rules/times here are ILLUSTRATIVE SAMPLE copy — layout stand-ins, not verified guidance.

Design decisions — frame B (ordering)

  • One section, not two: the fast spans the whole day; the puja is one act inside it. Fast facts frame the procedure, so the section heading becomes उपवास विधि · How to observe and the shipped PRD-19 vidhi card moves inside it, beneath the facts, keeping its own ॥ पूजा विधि identity row. Two sibling sections both subtitled "How to observe" would answer one question twice.
  • Vidhi-only pages are untouched: when a rule has a vidhiId but no upvas entry (today's six festivals until their entries verify), the block renders exactly as shipped — heading पूजा विधि · How to observe + card. Zero regression, pinned by the rendering-matrix test.
  • Moonrise-bound parana: Karwa Chauth's computed line is the occurrence day's PanchangData.moonrise — a different derivation kind than frame A, demonstrating the parana.kind enum. Null moonrise ⇒ rule text only.
  • Card behaviour unchanged: the vidhi card still deep-links to VidhiDetail with the occurrence's dateMs, same testID, same push-in-place navigation.

Design decisions — frame C (absence)

  • Absent, never placeholdered. This rule has no verified upvas entry and no vidhiId, so no "How to observe" section exists at all. This retires the parent PRD's original "Coming soon" slot and makes the PRD-19 Phase 2B house rule — never a placeholder — uniform across the page.
  • Draft = absent. The same frame is what a status: 'draft' entry produces: getUpvasInfo returns null for drafts, so an unverified entry is indistinguishable from no entry at every call site. Flipping to verified is a reviewed content change, not a code change.
  • No status language leaks: customer copy never says draft/pending/verified — the page just ends, quietly, at the ॐ-family seal spacing the readers use.
  • Test pin: the rendering-matrix Jest case asserts no placeholder string exists in this tree, alongside the three positive states.
