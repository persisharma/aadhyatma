What happens between these two frames

  • Nothing user-visible, and that is deliberate. Behind the held splash: preventAutoHideAsync() at module scope, the derived-cache reset and prefetchTodayPanchang() already in flight, five font families gating the provider tree, and AppReadyGate holding until font-scale + reading-language hydrate — because both change Home geometry.
  • Neither new feature may touch this path. §64's rule is that astronomy, prewarm, widget planning and schedulers all run behind InteractionManager after the reveal. PRD-23 is bundled data read on a detail screen — it never runs at launch. PRD-24's compass subscribes on screen focus, five taps deep, so it cannot either.
  • Reserved geometry still holds. Anything above the CATEGORIES grid must occupy its final space in frame one. Neither feature adds anything above the grid — PRD-23 adds nothing to Home at all, and PRD-24 adds only a DISCOVER card, below it.
  • The Today strip is already the door to journey A. That देवशयनी एकादशी chip is shipped behaviour; PRD-23 changes what the user finds two taps later, not the strip.

The only Home change in either PRD

  • One DISCOVER carousel card for वास्तु दिशा (Act 1). §32's carousel is explicitly the home for cross-cutting sections — Daily Practice, Sankalp, Pitru Smaran, पूजा विधि, Pilgrimage, Widgets — and it reshuffles per open, which is the right cadence for a surface consulted a few times a year.
  • No new grid tile. The grid is at 16 tiles (5 rows + the full-width नित्य साधना closer). A 17th tile for an occasional-use feature would break that closing row and claim daily real estate for an occasional need.
  • PRD-23 gets no Home presence whatsoever. It is never a destination — it is the answer to a question you already arrived with. Putting it on Home would invert the journey.

What this journey proves

  • PRD-23 is never a destination. Steps 1, 2 and 6 are shipped screens. The feature appears only at the moment the question is live — and the user never had to know the word "bhog" to get there.
  • Step 3 is the whole product argument. Today that screen answers whether and when to eat and stops. Everything a person standing in a kitchen needs is in the part that does not exist yet.
  • Step 5 loops back to a shipped store. vidhi/checklistStore.ts already persists ticks per-vidhi-per-festival-date at @vedansh/vidhi-checklist; the list extends that document rather than adding a second one, so the "fresh list each year" rule holds for free.
  • Step 6 closes the loop. The conduct card's नैवेद्य step can name the items from the same entry that drove steps 3–5, instead of a generic instruction.
  • Every new step degrades to today's screen. With no verified entry, step 3 loses one panel, step 4 loses one group, step 5 becomes the samagri list with a header. Nothing breaks; nothing shows a placeholder.

What this journey proves

  • Three entries, three jobs. The DISCOVER card is discovery (shuffled, occasional). The muhurat door is the moment of need — and it will carry most real traffic. The More row is the durable address they return to.
  • Step 3 is the cheapest high-value card in the batch. One occasion-gated door on a shipped result screen ends the app's largest asymmetry — 13 occasions dated, one explained — at the exact point the user feels it.
  • Step 4 exists because of a real gap. requestForegroundPermissionsAsync fires today only when someone taps "use my location" in Panchang. A user who picked their city from the list has never granted it, and trueHeading returns -1 without it. So the ask belongs here, with the manual path offered in the same sheet rather than behind a denial.
  • 5b is not an error screen. It is the second normal mode, and the manual grid is a peer path — which also makes the feature work on a device with no magnetometer and for someone reading a floor plan away from the house.
  • No new native dependency. The compass is Location.watchHeadingAsync() from the already-installed expo-location@19.0.8 — trueHeading arrives with declination already applied by the OS. The one binary-level change is the iOS purpose string, which must be widened before this ships.
Frame 5 drops the earlier prototype's "corrected for declination +1.2°" line — we are not the ones correcting it. If a provenance line is wanted, it should say the OS supplies true north.

The shape of the addition

  • 2 new screens. 3 in-place sections. 3 door/entry cards. 0 tab changes. Against an app that already ships ~80 reachable surfaces, that is the whole footprint of both PRDs.
  • Both features are answers, not destinations. PRD-23 has no Home presence at all and appears only where its question is already live. PRD-24 has one discovery card and one durable row, but its real entry is the muhurat result.
  • Neither touches launch, the tab bar, or Home's reserved geometry — so §64's first-frame contract, the 16-tile grid's closing row, and the Today strip's fixed height are all untouched.
  • Different blockers, so they can run in parallel. PRD-23 is cheap code waiting on content verification — ship the machine, entries at draft, invisible until reviewed. PRD-24's content is more reachable but it needs the iOS purpose-string change and a Phase 0 measurement of how often the compass is trustworthy indoors.
The one thing that would change this map: if Phase 0 finds accuracy: 3 is rare indoors, PRD-24's P1 should ship manual-dik-first and treat the live compass as the enhancement. Journey B's steps 4–6 stay identical; only frame 5's default state changes.
