PRD-16 §5 Phase 2 · TRD-16/P2 — grade the muhurat at the window, not at sunrise; solve Bhadra as an interval; give each occasion real masa rules; add six occasions.

Everything already shipped is drawn as it ships. The four Phase-1 screens, the answer block, the ListCard grammar and the struck-through Rahu Kaal row are all as-built; Phase 2 changes what those surfaces say, not how they look. Gold-marked captions call out the new behaviour.
All dates, times, angas and verdicts are real engine output — eventMuhurat.ts + panchangDayStore.ts for Ujjain, purnimant, 365 days from 14 Aug 2026. 2 · Bhadra becomes an interval — the single biggest yield change. Real output: 20 Aug 2026 carries Vishti at sunrise, so Phase 1 excludes the entire day. The solver puts भद्रा at 6:04–8:16 AM, and every auspicious window that day falls after it. Windows are dropped, not clipped: a partly-barred window is never offered as a shorter good one. Measured across a year: +26% to +45% qualifying days per occasion.

What Phase 2 actually costs

The four workstreams look similar in the PRD. In the source they are not remotely alike, and that determines the order.

WorkstreamCostWhy
Window-time angaFREE tithi.endTime and nakshatra.endTime are already solved and bisected (engine.ts:473-486). Grading at a window is endTime && t >= endTime ? index+1 : index — integer arithmetic, no astronomy. Highest correctness value of the four: 115 verdict flips a year.
Bhadra as a windowNEW SOLVER The only item needing engine work. karana.endTime is hardcoded null (engine.ts:495-499). A karana is half a tithi — boundaries every 6° of elongation vs 12° — so the solver is a parameterised twin of bisectTithiEnd, not a new algorithm. Largest yield gain: +26–45%.
Masa shuddhiCONTENT Code is a table lookup against the purnimant-normalised month. The work is authoring twelve occasions' month rules and settling three convention decisions that change real output.
Six occasionsCONTENT Pure EVENT_RULES entries. Annaprashan needs the age-window mode Namkaran already has; Upanayana is Chaturmas-barred and stricter.

Three decisions that must land before the tables are authored

  • Chaturmas reading. Shipped code uses tithi-span (Devshayani → Dev Uthani). Published lists appear to resume at Kartik Shukla post-Diwali — PRD §9.1's third reading, and the one §9.1 itself recommends. Measured cost of the current choice: 11 and 14 Nov 2026 excluded for Griha Pravesh while published lists include them. ≈2 weeks a year.
  • Dev Uthani off-by-one. The festival engine puts Dev Uthani on 20 Nov 2026; isChaturmasDay lifts the bar on 21 Nov. The day that ends the season currently sits inside it — and the 2026 Ekadashi is kshaya (PRD §9.2), so the boundary is contested downstream too.
  • Abujh factor gate. Phase 1 made abujh days lift the seasonal bars only, leaving 33 of 54 abujh×occasion pairs excluded — Dhanteras for all six occasions on factor match alone. Since §4.2 says these days need no panchang shuddhi, and nakshatra/tithi/vara matching is panchang shuddhi, this is the unresolved half.

Ordering

Steps 1–2 are code-only and can ship before the content review; 3–5 are gated on it.

  1. Window-time anga — free, highest correctness value
  2. Bhadra as a window — largest yield gain
  3. Masa shuddhi + the three decisions — needs §10
  4. Six new occasions — pure content
  5. Abujh factor gate — one line once decided

Two things that will bite

  • Kshaya stepping. On a kshaya day the next anga is not index + 1 — an index is skipped. PanchangData.kshayaTithi/kshayaNakshatra already carry it, so angaAt must consult them before stepping. This is the likeliest place for Phase 2 to introduce a silent wrong answer, and it gets its own test.
  • The cache version. Adding karana.endTime changes DayInputs, so PANCHANG_DAY_CACHE_VERSION must be bumped in the same PR (RULEBOOK §17.6). Miss it and every device that has already scanned keeps hydrating Phase-1 days forever — the fix reaching only fresh installs.

Phase 1 debt Phase 2 inherits

eventMuhurat.drikfixture.test.ts is still owed. It matters more now, not less: window-time evaluation is precisely the change that decides whether we agree with published lists on early-changeover days. Shipping Phase 2 without it means changing 115 verdicts a year with no external oracle. Rule tables also remain verified: false — the §10 review is still the release gate for the whole finder.
