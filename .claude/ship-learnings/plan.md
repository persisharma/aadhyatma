# /ship Learnings — plan phase

Learnings are auto-captured after each /ship run. Read before starting the phase.

### Verify repo is actually clean before claiming `create-expo-app .` will work at repo root

**Seen:** 1x — 2026-04-22
**Category:** plan-assumption
**Example:** Plan v1 claimed cuzco/ only had README+.git; in reality it had .claude/, .context/, .ship-* state files, and create-expo-app itself emits AGENTS.md/CLAUDE.md/.claude/settings.json by default. Scaffold collision was guaranteed.
**Resolution pattern:** Before planning a root scaffold, `ls -la` the target dir AND consult the tool's default-output manifest. Default to a subdirectory (mobile/, web/, etc.) for any non-trivial generator.

### Pin Expo SDK only after checking Expo Go store compatibility window

**Seen:** 1x — 2026-04-22
**Category:** sdk-lifecycle
**Example:** Plan v1 pinned SDK 55 to match reference app; on 2026-04-22 Expo Go App/Play Store builds were still on SDK 54 during the transition. Would have forced a dev-build setup before the first device run on a hello page. Fix: pin SDK 54, treat 54→55 migration as a separate ticket.
**Resolution pattern:** Before pinning an Expo SDK, check docs.expo.dev/sdk for the Expo Go transition state. If stores lag, pin the Go-compatible SDK unless dev-build is already in scope.

### ThemeContext is a structural contract, not a leaf concern — introduce useTheme() hook on day one

**Seen:** 1x — 2026-04-22
**Category:** architecture
**Example:** Plan v1 deferred ThemeProvider as "easy to port later". Reference app shows module-level `colors` frozen by `StyleSheet.create()` forces a deferred-require dance and a bundle reload on theme switch. Any screen doing `import { colors }` would need refactoring when ThemeProvider lands. Fix: `useTheme()` from the first commit, static light palette behind a context provider.
**Resolution pattern:** If screens will ever consume theme, expose theme via hook/context from commit one — never direct module import of mutable tokens.

### Blank-typescript template does not ship Expo Router — own index.ts explicitly

**Seen:** 1x — 2026-04-22
**Category:** template-assumption
**Example:** Plan v1 said "leave index.ts as generated by create-expo-app (it registers App via Router)". Wrong — blank-typescript ships no Router. Only default/tabs templates do. Fix: explicitly create index.ts with registerRootComponent(App) and set package.json "main": "index.ts" (matches CreditScore's mobile/index.js).
**Resolution pattern:** When choosing a create-expo-app template, check its README for entry wiring. blank* → own your own entry. default/tabs → Router is wired for you.

### Preview-first scopes belong in their own ship run, not crammed into a "full feature" ship

**Seen:** 1x — 2026-04-25
**Category:** scope
**Example:** User asked "create Gita section, but show me a one-screen preview first before shipping the full change." Cramming preview + full-section into one ship run creates weird phase boundaries (do you write acceptance criteria for the full section or just the preview?). Cleanest split: this ship delivers only the preview; a follow-up ship delivers the full chapter index + reader + 18-chapter parser.
**Resolution pattern:** When a user says "preview first", treat the preview as a standalone MVP with its own full ship cycle (plan → tdd → review → test → verify → eval → deliver). Stop at Phase 7 local commit (no PR) so the user can approve the design before Plan B begins.

### Don't extend an existing discriminated union for a new sibling module if it forces Hanuman code to know about Gita

**Seen:** 1x — 2026-04-25
**Category:** type-design
**Example:** Tempting to extend `Verse.type = 'doha' | 'chaupai'` to include `'shloka'` so one reader can serve both texts. But Hanuman's VersePage switches on `verse.type` and would need a `'shloka' never` branch (or handle it), leaking Gita knowledge into Hanuman code. Kept `GitaVerse` as a separate type. When a shared reader arrives in Plan B, we'll introduce a broader union at that layer.
**Resolution pattern:** Keep per-module types separate until a real shared consumer forces the merge. YAGNI beats premature union-widening.

### Audit source-data completeness in Phase 1 — don't discover gaps in Phase 5 simulator QA

**Seen:** 1x — 2026-04-25
**Category:** plan-assumption
**Example:** Plan said "all 701 verses have Hindi + English Commentary markers" based on `grep -c '**English Commentary**'`. True, but the marker existed for verses where the body was just a literal `.` placeholder (38/47 verses in Chapter 1). User saw empty "COMMENTARY" headings on the simulator and we had to patch the parser (drop thin paragraphs) + the reader (fallback note) after the fact. A five-line Python audit in Phase 1 would have surfaced this before any code was written.
**Resolution pattern:** When consuming third-party scriptural/legal/academic source data, audit body content length per section — not just section markers. Flag any section where >5 % of bodies are shorter than ~40 non-whitespace chars and decide the renderer's fallback up front.

### Don't silently substitute a "self-adversarial pass" when an external codex plugin is callable

**Seen:** 1x — 2026-04-25
**Category:** tooling
**Example:** Skipped `/codex:adversarial-review` across two plan rounds because `codex:adversarial-review` didn't appear in the skills registry at session start. Wrote "self-adversarial pass (no external codex harness in this environment)" — but skills and slash commands live in separate registries; the slash command was wired to `codex-companion.mjs` and callable, I just hadn't checked. User caught the shortcut.
**Resolution pattern:** If a ship phase references `/codex:*` or any external reviewer, try the invocation rather than inferring absence from a skills-list scan. When a real failure happens, surface the error — never quietly swap a real reviewer for a self-review.

### entryRoutes.ts has 5 routing functions, not 3 — count them before planning

**Seen:** 1x — 2026-05-24
**Category:** route-coverage
**Example:** Plan v1 said "register in navigateToEntryStart, buildProgressTarget, buildBookmarkTarget" (3 functions). Codex adversarial review found 5: also navigateToProgress and navigateToBookmark. Missing any one causes dead resume/bookmark links from that path.
**Resolution pattern:** Before listing registration points in a plan, `grep 'export function' entryRoutes.ts` and enumerate all public functions. Every routing helper that dispatches on entry ID or sourceId needs a new branch.

### backgrounds.ts runtime coverage validator will crash the app if entries are added without backgrounds

**Seen:** 1x — 2026-05-24
**Category:** boot-crash
**Example:** Plan had Task 14 (add LibraryEntry items) but Task 11 (register backgrounds) could easily be done after. The IIFE in backgrounds.ts runs on module import and throws if any active non-hidden library entry lacks a sourceBackgrounds mapping. Adding entries before backgrounds = app crash on boot.
**Resolution pattern:** When adding new library entries, always register their sourceBackgrounds BEFORE setting status to 'active'. Alternatively, add entries as `hidden: true` first, then flip to visible after backgrounds are wired.

### Single-chapter stotrams should use verse count in `sub` field, not chapter count

**Seen:** 1x — 2026-05-23
**Category:** data-convention
**Example:** Plan v1 used `'1 स्तोत्र · अर्थ सहित'` for krishna-stotram. Adversarial review caught it: multi-chapter stotrams (shiva=4, durga=3) show chapter count, but single-chapter ones (hanuman-ashtak, bajrang-baan, ram-stuti) show verse count. Fix: use `${total} श्लोक · अर्थ सहित`.
**Resolution pattern:** When adding a single-chapter section, check how similar single-chapter sections format their `sub` field in texts.ts. Default to verse count for single-chapter, chapter count for multi-chapter.

### Codex rate limits may require self-adversarial fallback — always attempt the invocation first

**Seen:** 1x — 2026-05-23
**Category:** tooling
**Example:** Codex companion hit OpenAI usage limit during adversarial review. Performed thorough manual code-verified adversarial review as fallback, checking 6 specific challenges against actual source files. The manual review caught the same sub-field wording issue that pattern-matching alone would have found.
**Resolution pattern:** Always attempt the codex invocation first. If it fails with a rate limit or auth error, perform a manual adversarial review verifying each challenge against actual code (not just reasoning about it). Document the failure and the manual findings.

### "New content since last update" must be content-ID-set diffing, NOT app-version comparison, when content ships via OTA

**Seen:** 1x — 2026-05-29
**Category:** design-mechanism
**Example:** NEW-chip plan proposed `addedInVersion` vs a stored `lastSeenVersion`. app.json has `runtimeVersion.policy: "appVersion"` → OTA updates CANNOT bump `version`, so version-based detection never fires for OTA content drops (the feature's own stated use case). Also the feature's debut release has no stored version for any user → everyone treated as fresh → nothing shows. Codex flagged both as high severity. Fix: persist a `knownIds` set; "new" = a discoverable library id absent from `knownIds`; `markSeen` adds to the set. Version-agnostic, OTA-safe, persists-until-tapped, no resurrection.
**Resolution pattern:** For "what's new since you last used the app" on an OTA-capable client, diff the current catalog of IDs against a persisted seen-set. Reserve version numbers only for a one-time debut seed. Verify against the actual update-delivery mechanism (OTA vs store build) before choosing version-based logic.

### Fresh-vs-upgrade detection must key off user-action-only storage keys, never mount-written ones

**Seen:** 1x — 2026-05-29
**Category:** race-condition
**Example:** To distinguish a returning user from a fresh install at a feature's debut, the plan scanned `AsyncStorage.getAllKeys()` for any `@vedansh/*` key. But sibling providers (NotificationPreferences writes `@vedansh/notif-meta`, UserActivity) write keys ON MOUNT during the same cold start, racing the detector → a genuine fresh install can be misclassified as an upgrader (and, here, would flip accessibilityLabels and break Maestro's fresh-install selectors). Fix: scan only keys written exclusively by deliberate user action in a prior session (bookmarks, reading-progress, search-recent, japam-counter, language); exclude any key a provider may write on mount.
**Resolution pattern:** When using "does prior app data exist?" as an install-vs-upgrade signal, enumerate which keys are written on mount vs. only on user action, and gate on the user-action-only subset. Also seed/diff only user-discoverable (active && !hidden) ids so prelanded hidden/coming content isn't silently pre-acknowledged.
